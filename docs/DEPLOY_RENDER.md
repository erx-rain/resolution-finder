# Deploying the Resolution Finder on Rain's own Render account

The service used to run on an agent-managed Render account (`agentbase-prod`)
that nobody at Rain could log in to. This file moves it to an account Rain
controls.

## 1. Create the service (about 5 minutes)

1. Log in to Render with Rain's account.
2. **New → Blueprint**, connect GitHub, pick `erx-rain/resolution-finder`.
3. Render reads `render.yaml` and shows one web service (`resolution-finder`,
   Standard plan, 1 GB disk). It will ask for:
   - `RF_GITHUB_TOKEN` — a **new** GitHub token with only the `gist` scope
     (read access to the market gist). Do not reuse the old token; it leaked.
   - `RF_SERVICE_TOKEN` is generated by Render automatically.
4. **Apply.** The first build takes several minutes (it installs torch).
5. When it shows **Live**, open `https://<service>.onrender.com/health` —
   it should return `{"ok": true, ...}`. The logs should show
   `NLI verifier loaded — scans are ready` within a minute or two.

## 2. Point rain-admin at it

In Vercel → rain-admin → Settings → Environment Variables (Production, and
Preview if you test there):

| Variable | Value |
|---|---|
| `RESOLUTION_FINDER_BASE_URL` | `https://<service>.onrender.com` |
| `RESOLUTION_FINDER_TOKEN` | the `RF_SERVICE_TOKEN` value from Render → service → Environment |

Redeploy rain-admin. The token stays server-side: the browser only talks to
`/api/resolution-finder/...`, which adds the token on the server.

## 3. Check it end to end

Market Wizard → Resolution Finder → pick a market → **Run scan**. The job
should go queued → running → done and a finding should appear. Or from a
terminal:

```bash
B=https://<service>.onrender.com; T=<RF_SERVICE_TOKEN>
curl -s -X POST -H "Authorization: Bearer $T" -H 'Content-Type: application/json' \
  -d '{"market_id":"6a60c0a9f8e64ced2c3da4e8"}' $B/scans
curl -s -H "Authorization: Bearer $T" $B/scans/<job id>
curl -s -H "Authorization: Bearer $T" $B/markets/6a60c0a9f8e64ced2c3da4e8/findings
```

## Why these settings

Measured on 2026-10-12 with CPU-only torch, one real scan of the
Tesla/SpaceX market:

- memory after importing the engine: **433 MB**
- peak memory during the scan: **586 MB**
- scan time: 13 s (models already downloaded)

So the 512 MB Starter plan cannot run scans — that is exactly why the old
service restarted mid-scan and lost the job. Standard (2 GB) leaves room for
both models and the request threads.

Cost on Render's own pricing: Standard web service about $25/month plus
about $0.25/month for the 1 GB disk, billed to Rain's Render account.

Other details:

- **One worker only.** The job queue is in-process; extra workers would each
  have their own queue. Use threads, not workers.
- **Disk at /var/data.** Findings, run history, the schedule and the
  downloaded models live there and survive restarts and redeploys. A
  Render service with a disk cannot scale beyond one instance — fine here.
- **Gist read on every request.** No caching of the market list.
